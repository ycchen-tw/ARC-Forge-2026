**Core rule**: The board contains **blocks** and **hollow target frames**. **Every frame** must contain a block of the matching type and exact size, inset 1px from its upper-left corner; the frame is 2px wider and taller than the block. The check does not require every movable object to enter a frame. Ordinary blocks and special blocks match ordinary and special frames respectively. Block shapes include 3×3, 6×3, 3×6, and 6×6, with corresponding 5×5, 8×5, 5×8, and 8×8 frames: **shapes must match**. When a pushing block hits an object, the pusher stays still and the struck object flies away, rather like a billiards break.

The visible 9×9 special blocks and their 11×11 target frames are cross-shaped; these dimensions describe their bounding boxes, not filled rectangular patterns.

**Actions**
- `ACTION6(x,y)`: Click a block to make it the **currently controlled block**. **Only ordinary blocks are selectable** (`get_sprite_at(..., "0022vrxelxosfy")`); 9×9 special blocks and bombs cannot be selected and can only be struck or blasted.
- `ACTION1/2/3/4`: Up / down / left / right, pushing the current block **3 pixels** (= 1 logical cell). Hitting a wall leaves it still.
- **On hitting another object, you do not move at all**. The struck object is pushed in the same direction by up to **15 pixels (5 logical cells)**, recursively pushing objects encountered along the way. A wall may stop it early, while ice may make it slide farther. A failed chain restores only the pusher currently being processed; downstream objects already moved are not guaranteed to return.
  (`loydmqkgjw` restores the pusher's position and returns the struck sprite; `step()` then puts them in a pending list, advancing it by 3 coordinate units per frame while `xrxdckwsth < 5`. Measured: block A strikes block B at x=18; A stays put and B ends at x=33.)
  - **Additional measurement**: When a chain is blocked, the official implementation restores only the “foremost pusher”; **downstream objects already pushed do not rewind** (`ifoelczjjh` restores only itself).
- Every directional action and every `ACTION6` costs one unit of budget, including blank clicks and reselecting the same block. Blank clicks retain the current selection. No Undo. All movement/collision/explosion animations resolve within the same action and cost only once.

**Two additional mechanisms**
- **Ice** (large color-15 regions):
  - For **the step you directly control**, ice **acts as a wall**: any overlap with ice at the destination cancels the whole step. The selected block can never step onto ice (`loydmqkgjw` checks ice `0015qniapgwsvb` together with wall `0029ifoxxfvvvs` and restores position). Crossing ice requires an impact or blast.
  - Struck/blasted objects **can** enter ice: after their normal travel distance, **they keep sliding while still on ice**, until leaving it or hitting something (`dgjbrykwhi` stops only at `xrxdckwsth >= 5 and not on_ice`). Only walls block flight; **ice does not**.
- **Timed bombs** (color-12/13 blocks; themselves pushable, so they can be struck or blasted by other bombs):
  - Each **movement action** charges one row, with color 12 filling from the rear toward the muzzle. `ACTION6` selection **does not** charge bombs, but a blocked movement still counts; pushing against a wall is therefore a valid wait. A 6×6 bomb takes 6 turns, a 3×3 bomb 3 turns.
  - When full, it **explodes**: a column-shaped shockwave **as wide as the bomb, extending 3 logical cells forward**, expands in three stages. Each stage tries to push objects in its area by 1 additional logical cell (3px). With a clear path, objects in cells 1 / 2 / 3 measured from the bomb's front edge are pushed 9 / 6 / 3px respectively, to cell 4. Objects landing on ice continue sliding.
    - Those displacements assume **a clear path with no interference from simultaneous explosions**. Walls, blocked chains, and ice can all change endpoints. The staged shapes differ for 3-pixel-wide and 6-pixel-wide bombs (`explode-3-i` covers “exactly cell i” in each stage; `explode-6-i` covers “cells 1..i”). Fixed endpoints should not be treated as a universal rule.
  - **An exploded bomb does not become debris**: `pxqdkrdaye` fills it entirely with color 13, resetting its charge to zero. Charging starts again on the next action, **cycling indefinitely**. Bombs can help send blocks to distant frames, or blast a carefully positioned block back out.

**Measured corrections (missing or incorrect in the original document)**

1. **An uncharged bomb's muzzle direction is invisible.** On entering a level or immediately after an explosion, it is entirely color 13, so all four orientations look identical. Only after the next movement action fills the first color-12 row can direction be read: color 12 is at the rear, with the muzzle opposite. Bombs in levels 6 and 7 start at 0 charge, requiring one initial action to charge and probe their direction.
2. **Explosion cleanup reactivates “old velocities of objects on ice.”** Velocity table `ooneovlmbq` **is never cleared during a level**. When the last explosion stage ends, the official implementation pushes **every pushable object ever assigned a velocity that is currently on ice** another 3px along its old direction, including objects untouched by this explosion. If any object slides successfully, cleanup repeats until all leave the ice or are blocked; it is not limited to one extra slide. Offscreen bomb explosions also trigger this.
3. **Color 4 has two roles.** An empty frame's outer border is color 4; a previously selected but currently unselected block's center is also color 4. A never-selected block has center color 5; the current block has center color 0. Also, **the entire side of a selected block's border next to another movable object is painted color 0** (`qfbbmqfhwa`). Recognize blocks by border color 14, because only blocks use color 14 in the entire game.
4. **Wall boundaries need not align to the 3-unit lattice.** A level-4 wall ends in the middle of a cell: displayed x=32 is wall, floor begins at x=33, and the lattice phase is 2. Collision uses individual pixels, so even one wall pixel in a cell makes it unstandable.
5. **`Enemy` / `lose by enemy` is dead code.** `omeizjufss` / `dxnwjisewh` pursues `0001uqqokjrptk`, but none of the 7 levels has any sprite tagged `Enemy`, so it never runs.
6. **The special block in level 5 is not a victory requirement.** This 3×3 `0006xssgmrgoep` sits offscreen at x=-9, and that level has **no** 11×11 special frame, so `dbmlcqbquh` imposes no requirement on it. Level 5 only requires putting the single 3×3 block into the single 5×5 frame.
7. **3 more 3×3 bombs in level 5 are also offscreen.** Their shockwaves hit nothing. Their only observable effect is to trigger the ice-sliding cleanup in item 2 every 3 directional actions; selection does not charge them.

**Winning, losing, and resetting**: Once an action fully resolves, check all frames first; success advances the level, otherwise remaining budget 0 loses. With budget N, action N can still win. Selection does not advance the bomb clock but can still exhaust the budget. Entering each level selects the first ordinary block and rebuilds the budget, old velocity table, and pending flight/explosion lists; nothing carries over from the preceding level.
