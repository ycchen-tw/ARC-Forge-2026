**Core rule**: The map is divided into **rings**, each a cyclic sequence of cell positions. The code numbers these cells 1..N. Direction `R` means `i → i+1`, wrapping N to 1; direction `L` means `i → i-1`. Clicking a button **moves every block on that ring one position around the cycle**, like turning one layer of a Rubik's cube. An empty position does not produce a block; the hole simply moves around with the rest.

Ring shapes vary: rectangular loops, diamond loops whose successive cells can be diagonal, winding paths, and even **straight line segments**. Closing a straight segment into a cycle appears as a block disappearing at one end and appearing at the other, like teleportation. In level 4, each of the two rings is split into 4 segments across the four corners, linked entirely by these jumps. **Successive ring positions need not be adjacent onscreen**: in level 6, ring B advances by 2 cells per step and ring C by 3.

**Buttons**: Drawn as notched 3×4 blocks; **color 8 means `L`, color 14 means `R`**, for every button. A button's **sprite definition** can be reused for several **placed instances**, and multiple instances can overlap at one location. **Summing distinct clickable locations within each of the eight levels gives 51**. A button sprite **may be rotated 90°**, appearing as 4×3 onscreen (level 4's ring-B buttons, level 6's 25/26/27 buttons, and level 7's ring-B buttons all use `set_rotation(270)`). However, **not every ring has a pair of buttons**:

- All **36 rings in level 6 have only `R` (color 14) buttons**. Movement is one-way; use wraparound to return.
- Level 7's ring C **has no button at all**. Other rings must move blocks into it to park them there.

**One button can drive several rings simultaneously**: The official implementation **stacks multiple button sprites at the same coordinates**, then click handling retrieves all sprites covering the clicked point and triggers each. One click therefore rotates every ring in that group by one position. Measurements across all button groups in all 8 levels found that rings within a group never share positions, so no block moves twice. This is the main source of difficulty in later levels:

- Level 6: 7 clickable buttons drive groups of 8 / 8 / 8 / 3 / 3 / 3 / 3 rings.
- Level 7: ring-A and ring-D buttons overlap, so one click rotates both.
- Level 8: rings D / E / F share one pair of buttons.

Different rings **share positions**: rotating A can move a block onto ring B's path. This is central to the puzzle.

**Victory condition**: Move all target blocks onto their matching target cells; two block types each have their own target type. In code, a “target cell” is a stationary 4×4 corner frame, color 11 or 12, with only its four corners drawn. A “block” is a moving 2×2 color patch carried by rings. Other 2×2 patches, colors 1 / 2 / 9 / 10 / 15, are neutral blocks that only make ring movement visible. Target blocks of the same color are interchangeable. The check asks whether every corner frame has a same-colored target block at its center position.

**Layout geometry**: Positions are spaced 3×3 apart. A 2×2 block starts at a position's upper-left corner, always at coordinates divisible by 3. A 4×4 corner frame starts **one coordinate unit up and left** from that position, at coordinates ≡ 2 mod 3. Frame pixels and block pixels therefore never occupy the same pixel phase. The official implementation moves only sprites whose upper-left corner exactly equals the ring position, so frames and buttons stay stationary.

**Budget**: Only **actually clicking a button** spends budget; blank clicks are free and do not recheck victory. Driving several rings still costs only once. **The winning click costs no budget**: `step()` checks victory first, then subtracts budget, then checks for loss at 0. A `StepCounter = N` therefore allows “N−1 nonwinning clicks, with click N required to win directly.” Changing levels resets both budget and board; no Undo. Human baselines are official per-level action statistics and differ from this internal counter, which charges only effective button clicks. Level 8's current baseline 159 (old definition 173) cannot directly be treated as a route length under the internal budget of 80.

**Common mistakes when reading the obfuscated source statically, corrected by measurement**

**The viewport does not scroll.** The game constructs a 16×16 Camera, but official engine `ARCBaseGame.set_level()` overwrites its view with the level's `grid_size`. The actual image is the **entire map scaled/padded to 64×64**, without scrolling. The 4 copies of each level-4 button at the corners are simply for convenient layout.

**“Visible blocks” are not the same as “ring positions.”** Level 8 has 24 purely decorative 2×2 blocks on no ring: some form a full column and the rest are scattered elsewhere, also resembling blocks on rings. Conversely, 3 of level 7's 17 ring positions are empty. Patterns can suggest candidate paths, but cannot uniquely determine ring positions, order, and jump connections; compare movement before and after button presses to establish topology.

**Adjacent corner frames can produce a false frame.** Because frames draw only four corners, the regularly spaced frames at (23,26)/(29,26) in level 6 and (23,50)/(29,50)/(35,50) in level 8 create another valid-looking 4×4 corner frame between them. Correct counting requires a set cover with “exactly n frames covering all corner pixels,” where n is the number of blocks of that color.

**The HUD obscures board pixels.** The progress bar occupies all of column 0; level cells occupy x=10..48 on row 1. `y_offset` is 0 in levels 5/6/8 and `x_offset` is 0 in levels 1/8, so these HUD pixels directly overwrite the board. Fortunately, at least one pixel remains visible for every 2×2 block. The level-cell condition is `i <= level_index - 1`, so no cell is lit during level 1.
