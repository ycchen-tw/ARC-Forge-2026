> Paragraphs marked **[Correction]** below identify mistakes in the original static reading.

**Core rules**: Direction keys move all avatars on the board **simultaneously**, applying a different reflection to each:
`toljda-leklkn`=(dx,dy), `toljda-rivmdg`=(−dx,dy), `boweok-leklkn`=(dx,−dy), `boweok-rivmdg`=(−dx,−dy).
The goal is to have all avatars **move onto the same cell and overlap**; overlapping pairs are marked complete, and completing all pairs clears the level.
An avatar that hits a wall stays put—**using walls to break the mirror symmetry** is the central solution technique.

**[Correction] All six levels have only two avatars, always the `toljda` pair** (only dx is reflected; dy is shared).
The two `boweok-*` sprites are defined but **used in no level**; the four-avatar/four-quadrant branch is dead code.

**[Correction] There are two overlap tests; the second recognizes only horizontal adjacency**

1. The two avatars end a step in the same cell.
2. A “swap” fallback: the avatars **were horizontally adjacent on the previous step** (`|Δx| == 1` and `Δy == 0`), and on this step one
   moves into the other's previous position → both are pulled to the midpoint of their current positions (`//2`, i.e. the cell on the left) and merge.
   **A swap between vertically adjacent avatars does not count**; the source checks only `abs(x1-x2)==1 and y1==y2`.

**[Correction] The two `psqw` colors paint the walls, not the background**: The interface recolors **every color-0 pixel in the entire frame**
with these two colors (the first for screen x<32, the second for x>=32). The wall sprites themselves use color 0,
and the letterbox background is also 0, so **the walls and screen border share colors, and the wall colors vary by level**. What stays fixed
is **floor = color 5** (camera background). When recognizing terrain from the image, the only reliable anchor is floor color 5,
not the walls. The four-quadrant branch is reached only with four avatars, so it is unused in this game.

**Action mapping**

- `ACTION1/2/3/4` = up/down/left/right, moving all avatars (with their respective reflections).
- `ACTION6(x,y)`: Clicking `mosdlc` (a color-9 pushable block) selects it and turns it color 11; direction keys
  then **move that block remotely: no avatar needs to be adjacent, and the avatars stay still**. Clicking **any non-block cell inside the board** (including a wall, trap, or an avatar's own cell) deselects it.
  **[Correction]** Clicking **outside the board** (the letterbox) is a complete no-op: it does not even deselect,
  but still consumes one action.
- **[Correction]** While a block is selected, all unfinished avatars are `color_remap`ped to **color 1**; only deselecting returns them to
  color 10. Thus avatar colors on screen change with the selection state.
- **[Correction]** `ACTION5` has no effect, but **still consumes one action** (measured `_action_count` 0→1).

**Three kinds of terrain components**

- `wahtyt-LevelN`: The wall maze, different in each level (**level 6 has no wall sprites at all**; the boundary is a full ring of traps).
- `spswjz` (color 8): Trap cells. **[Correction]** The interface overlays a **color-5 checkerboard pattern** where `(x+y)%2==1`,
  exposing color 8 on only the other half, so a trap cell alternates 8/5 rather than being solid. Any avatar stepping on one → blinking for
  **7 engine ticks (8 frames for the entire action)** → **all `sys_click` sprites (both avatars
  and pushable blocks) return to their level starting positions**, with no action refund. Already completed pairs remain completed.
  Trap handling precedes merging; an action that steps on a trap does not check for a meeting. **Gates are not updated immediately after positions reset**, so a previously opened gate may temporarily remain open until the next avatar or block branch calls the gate update; merely selecting a block does not update gates.
  **[Correction]** When an avatar stands on a trap cell, the interface **skips** its checkerboard pattern (`fucr` tag, present on both
  `toljda` avatars), so the trap is invisible during those animation frames.
- `gayktr-{grwjuk,orfrpe,puvdux}` (3-cell gates in colors 14/12/15, all placed with `rotation=90` as a
  **horizontal** line in the levels) + `unobxw-*` (1-cell buttons in the corresponding colors): Whenever an avatar **stands on any** button
  of a color, **all** gates of that color receive `set_interaction(REMOVED)`; leaving restores them.
  **[Correction]** There are three pitfalls for an observer using only images:
  (a) An open gate is `REMOVED` = **completely invisible**; its cells look like floor;
  (b) An avatar standing on a button **covers it** (avatar layer 2);
  (c) **A gate can close on an avatar**—collision is checked only at the moment of movement. If an avatar enters an open gate and its partner
  leaves the button, the gate returns under its feet, leaving only two of its cells visible. All three make a single frame incomplete evidence.
- `mosdlc` (color 9): A selectable pushable block that blocks avatars (tag `xbso`). The interface draws a **color-5** outline
  around its cell, so a block cell has “border 5 + interior 9/11”.

**The collision rules are asymmetric (easy to misread)**

- Avatars (`jpwxcqabja`) check only **wall tag `wahtyt`, block tag `xbso`, collidable `gayktr-*` gates**,
  and level boundaries. **Avatars do not block each other** (otherwise they could never merge), **nor are they blocked by traps or buttons**.
- A block (`try_move_sprite`) rolls back its entire move on hitting **any** collidable sprite, so **a block cannot be pushed onto a trap
  or a button**, and cannot push another avatar or another block.

**Level 3 is the real difficulty** (its human baseline under the old metric was only 83, which was misleading; the current metric is 203): The sole passage between the left and right halves, (6,2),
is blocked by a block; the sole passage between the upper and lower parts of the left half, (1,3), is also blocked; and the row 6 corridor in the right half is blocked by
(8,6). The route found in the old reconstructed engine moves all three, pushing (8,6) to (11,6); A* in that model found **no solution within 40 steps**. This is a historical search result; neither the shortest path nor the claim that “the blocks must be pushed this way” has been reproved on the current official engine.

**The action limit is 150 per level**: The official `ARCBaseGame.set_level()` resets `_action_count` to zero on entering a level; the game declares a loss when `_action_count > 150`. The old draft inferred a per-level reset from the six levels' shortest paths totaling ≥167; direct reading of the official 0.9.3 engine now confirms it, so this inference is unnecessary.

The official engine increments the action count **before** `step()`: Action 150 is still processed, while action 151 immediately loses and cannot be used to complete the meeting. Hitting walls, selecting/deselecting, clicking outside the board, and `ACTION5` all consume the allowance; animation adds no extra counts. A new level resets avatars, blocks, selection, and the completion set; a trap only resets positions and is not equivalent to restarting the level. There is no undo key.
