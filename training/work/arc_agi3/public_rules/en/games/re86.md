**Core rules**: The background is a **blueprint** scattered with **3×3 small markers**—the outer ring is color 4,
and **only the center cell specifies the required color**. There are also several movable **wireframe shapes**.
The condition for clearing the level is: **Every marker's center cell must be covered by a line of the same color**.
The check uses the **topmost pixel after compositing shapes in list order**: An upper line of a different color covers a previously correct line below. Shapes can pass through each other without blocking; recolorers, reshapers, and the selected shape's white dot are not additional targets to cover.

The implementation (`jeiavrvavi`) composites all shapes onto a **blank** canvas (the blueprint itself is not part of the composite),
then requires **every pixel in the blueprint sprite that is neither -1 nor color 4** to equal the canvas pixel at that location.
The color-4 outer ring is entirely excluded from the check; it is only a visual aiming guide. **Shapes can hide marker centers or rings even in the initial frame**. Move shapes to inspect what they covered; a point missing from the first image is not necessarily absent.
Strictly speaking, this is therefore a **point coverage** condition rather than “fill the entire outline”—although a shape is usually pinned by 2-4
marker points at once, effectively fixing its position, size, and color.

**The shapes on the board are not all “hollow boxes”.** The 20 movable sprites fall into five wireframe families. Table dimensions use **height × width**: `1×43` is a horizontal line, and `19×37` is a cross 37 wide and 19 high:

| Family | Appearance | Levels |
|---|---|---|
| Cross `＋` | A vertical bar + a horizontal bar spanning the bounding box | 1,2,4,5,6,7 |
| Diagonal X | The two diagonals of the bounding box | 2,3,4,5 |
| Diamond `◇` | A box rotated 45° | 2,3,5 |
| Hollow box | Only the four edges | 6,7,8 |
| Thin line | One 1×43 line | 3 |

Actual hollow boxes appear only in levels 6-8, and are precisely the only type whose dimensions are changed by reshapers
(the boxes and diamonds with the `0036ilsgwuvbxv` tag in the source).

**Action mapping**

- `ACTION1-4`: Move the **currently selected shape** by 3 cells.
- `ACTION5`: Switch to the next shape (the selected shape's center is painted with a color-0 white dot).

The directions are 1 up/2 down/3 left/4 right. **Moving, hitting a boundary, failed reshaping, and switching all cost 1 step**; there is no undo key. After an action completes (including its recoloring animation), all markers are checked before testing whether the step count has reached zero, so **the final unit of allowance can clear the level**. A new level resets all shapes, devices, selection, and step count, retaining no recoloring, size, or position from the previous level.

Boundaries constrain only the shape's **center point** (`rtivumgcjd` checks only `x + w//2`, `y + h//2`),
so more than half a shape can hang offscreen—the correct placement of the color-11 cross in level 1 has its bounding box at y = −2.

**Two modification devices** (neither blocks movement; shapes move directly onto them)

Devices can also be clipped by the screen edge: L8's leftmost 5×5 recolorer shows only 2 columns. Its visible width in one image need not be its full size.

- **Recolorer** (5×5 or 6×6, color-2 border, solid 3×3/4×4 interior of a single color): A shape touching it is recolored **entirely**
  to that color. An animation spreads outward from the contact point, but finishes **within the same action**
  (one trigger in level 4 was measured to render 27 frames, while `action_count` increased by only +1),
  requiring neither extra actions nor extra steps. A shape already in that color does not trigger it and can pass straight through.
  **When several recolorers are touched at once, the winner is the earliest one in the sprite list whose color differs from the shape's**
  (`ucpbzrcoui` does `return` at the first match)—that order cannot be read from the image, so the pixel solver
  treats any move that “simultaneously touches two or more recolorers of a different color” as nonexistent. [Confirmed by measurement]

- **Reshaper** (a color-1 block): The only device that changes a shape's dimensions/proportions. **Its effects on the two types of shape differ completely**:
  - **Hollow box/diamond**: Horizontal collision → height +3, width −3; vertical collision → height −3, width +3
    (horizontal collision adjusts y and rounds to the nearest multiple of 3, while vertical collision adjusts x; a left/up collision also retracts the original −3 translation, while a right/down collision retains the +3 translation, so the center cannot generally be treated as fixed). If the side being hit is ≤ 6, the reshape fails and the shape bounces back.
    Three consecutive collisions with the 19×19 box in level 6 were measured as: 19×19 → 22×16 → 25×13 → 28×10.
    Incidentally, this code **unconditionally redraws a rectangular outline**, so a diamond hitting it would turn into a box—
    but diamonds and reshapers never coexist in the official 8 levels, so this path is unreachable there.
  - **Cross**: The bounding box dimensions stay entirely unchanged; what changes is **the bars' positions within that box**. The moving bar is always
    **the one corresponding to the push axis** (a horizontal push moves the vertical bar; a vertical push moves the horizontal bar). Its movement depends on whether,
    **after the push**, the absolute coordinates of the two bars each lie inside the reshaper's bounding box
    (the vertical bar's x is tested against `[zx, zx+zw)`, the horizontal bar's y against `[zy, zy+zh)`).
    **The three cases differ completely** [confirmed by measurement]:
    - **The corresponding bar is hit** (for a horizontal push, the vertical bar lies within the x range) → the bounding box continues sliding forward by 3 cells,
      while that bar's index moves back by 3, effectively **pinning the bar in place** as the arms on either side trade length.
      Measured leftward pushes of the 25×25 cross in level 6: bounding box (24,12) → (21,12) → (18,12),
      vertical-bar column index 12 → 15 → 18, with its **absolute** x always 36.
    - **The other bar is hit** (for a horizontal push, the horizontal bar lies in the y range, while the vertical bar is outside the x range) →
      **the entire bounding box bounces back to its original position**, but **the corresponding bar moves 3 cells in the push direction** (still the vertical bar).
      Measured in level 6: A 25×25 cross at (36,21), vertical bar x48, horizontal bar y33, pushed left once →
      bounding box still (36,21), vertical bar now x45. The vertical counterpart: Cross at (18,3), vertical bar x30, horizontal bar y15,
      pushed down once → bounding box unchanged, horizontal bar moves from y15 to y18.
    - **Both bars are hit at once** → the whole shape bounces back, with nothing changed.
    Also, when the bar is already at the bounding-box edge (for a horizontal push, `c == 0` or `c >= w-2`; analogous vertically),
    the first case bounces the whole shape back, while in the second case only the bounding box bounces back and the bar stays unchanged.
    The color-9 cross in level 6 requires this modification; translation alone cannot cover its four markers.

  > **The official code has an unreachable out-of-bounds bug here** [confirmed by measurement]: Moving a bar directly writes
  > `pixels[r + 3]` while checking only `r < height - 2`, with no upper-bound check, so `r == height - 3`
  > causes IndexError (negative indices do not; numpy wraps to the other end). None of the cross dimensions and bar remainders in the 8 shipped levels
  > can produce that combination, so it does not occur in official play; however, **a solver inferring dimensions from pixels
  > can generate hypothetical dimensions that do produce it**, and those transitions must be removed outright as “nonexistent edges”.
