## SK48 — Arrange colors with robotic arms (telescoping arms / Snake)

[Chinese source](../../games/sk48.md)

Some boundary behaviors labeled “test-based correction” below retain probes from the old reconstructed engine and were not individually retested on the official engine.

The level-5 human baseline of 230 (304 under the old definition) cannot be compared directly with 196: the latter charges only directional inputs. **ACTION6/ACTION7 cost no steps**, but are still game actions.

**Core rules**: The board contains **paired** robotic-arm bases (a pair has the same color in the base's central 2×2). Each base extends an arm of square segments in one direction. **Colored blocks** are scattered around. Extend, retract, and translate arms to position blocks underneath them. The goal is for the sequence of colors **currently beneath** an arm's segments to match its partner's sequence. Each compared position has a check light; all lights lit means success.

**Only the board arm in each pair may be controlled; the lower one is a fixed template**. Pairing is established only for bases **above the budget bar (row 53)**. Their partners sit on row 56 (the HUD strip below the bar): each partner arm is a **stationary template**, already carrying the target block sequence, with the check lights also drawn on it. When `ACTION6` hits a paired base tagged `sys_click`, either the board base or its lower template selects the **board** arm. Neither pair in current level 4 has that tag, so switching is impossible. (Evidence: `on_set_level` builds pair table `xpmcmtbcv` only under `if bcwsrdcswp.y < fzjeqdahvs:`; after `if pgoezovmf in [bcwsrdcswp, pphvqzjirf]`, the ACTION6 branch of `step()` always calls the key, the upper arm. Check lights `jdojcthkf[partner]` belong to the partner. All eight levels have template arms at y=56. All tested cases agree.)

**The number of compared positions is “template segment count − 1,”** rather than “number of blocks on the template.” One light is created for every segment after the template's first (`for kohhdjrfgt in self.mwfajkguqx[pphvqzjirf][1:]`), and comparison iterates only over the lights. In all eight levels, every template segment except the base segment happens to have a block underneath, so the two counts agree; their meanings differ.

**Victory depends on the current state, rather than a history of colors swept over**. Each evaluation clears and rebuilds the sequence: scan **whether each arm segment has a block beneath it**, from the base outward, recording colors and skipping empty segments. The sequence changes immediately as blocks move; nothing accumulates. Comparison stops at the number of lights. Extra blocks beneath your arm are harmless, provided the **first required colors** match in order. (Evidence: `gvtmoopqgy()` calls `self.vjfbwggsd[base].clear()` each time, then rescans `mwfajkguqx[base]`; the comparison loop is `for i, light in enumerate(self.jdojcthkf[partner])`, failing for missing entries only when `i >= len(vjfbwggsd[base])`.)

Equivalently: **goal ⟺ “the first N block colors on the base's line, before any obstacle, from inside outward equal the template sequence,” with the arm extended far enough to cover the Nth block**. Overextension is fine.

**Actions** (movement semantics require the most inference here)
- `ACTION1-4` (up/down/left/right respectively) have three effects, depending on direction:
  - Press **along the arm's facing direction** → **extend** by one segment.
  - Press **opposite its facing direction** → **retract** by one segment (it cannot retract below one segment; the attempt still costs a step).
  - Press **sideways** → translate the whole arm only if there is a **rail** between the base and the adjacent cell on that side. This is **all or nothing**: if any segment (or a block it must push) cannot move, the whole arm stays put.
    The probe point is `get_sprite_at(base.x + 2 + dx//2, base.y + 2 + dy//2, "irkeobngyh")`: the pixel on the base cell's midline, one pixel beyond its edge in that direction.
- `ACTION6(x,y)`: switch arms only by hitting a base **both tagged `sys_click` and present in the pair table**; the tag is not visible.
- `ACTION7`: **Undo**, restoring base/block positions and arm lengths from before the previous completed move, repeatedly if needed. **The currently selected base is not rolled back**. Selecting an arm, blank clicks, and unsuccessful directional moves do not create normal movement saves.

`ACTION6` and `ACTION7` **both cost no steps** (`qiercdohl -= 1` appears only in directional-input handler `hgivzuhjvj()`). Undo does not refund spent steps either, so it cannot restore the budget. Even invalid directional inputs (such as a direction without a rail) cost 1 step.

**Outcome and animation order**: A directional input deducts a step before moving. One 6-pixel cell is animated at 3 pixels per tick; new input cannot interrupt it. Once movement finishes, all pairs are checked first. If the last step makes every comparison pass, **you win even at 0 steps**; otherwise 0 steps loses. A completely ineffective final step loses immediately. Changing levels rebuilds a clean board, restores 196 steps, reselects the first base, and clears Undo, push highlights, and animation.

**Blocks cannot block arm extension**. Extension checks only whether the cell beyond the outermost segment would leave the bounds or hit an obstacle (`if self.qzvlbxkjgk(mwfajkguqx[base][-1], move_x, move_y): return`). Colored blocks in the way are **pushed forward**, including chains. If they cannot be pushed, **extension still succeeds and the arm slides underneath them**. This is how to “pick up” a block: first push it until pinned against the boundary, an obstacle, or a perpendicular arm, then extend one more segment underneath it.

**There is only one way to release a block: retract**. Retraction drags blocks within the arm's reach back by one cell. **An immovable block does not stop retraction; the arm instead withdraws from beneath it**. This is the only operation that can leave a block behind. Translation always carries the whole row of blocks beneath the arm, so to “put it down and leave,” first pin the block against a wall, obstacle, or perpendicular arm, then retract. (Evidence: `elif (segment_dir_x == 0) != (ledwmfklzk == 0): return False` fails the entire move only when the segment orientation is perpendicular to movement; an unpushable block in the parallel direction is simply skipped.)

**When blocks cannot be pushed**: The destination is outside the bounds, is an obstacle, a downstream block in a chain cannot move, or either the current or destination cell lies beneath **another arm perpendicular to movement** (`pptqisyill` finds perpendicular segments). This last rule means **perpendicular arms pin blocks**: a vertical arm acts like a row of clamps; blocks underneath cannot be pushed sideways and can only be carried along its direction.

**(Test-based correction) Blocks push other blocks in chains, and this is the only way to reach blocks the arm cannot reach itself.** The earlier document mentioned chains only as a failure condition, but they are central to levels 5 and 6. For example, the obstacle at (29,24) cuts off the arm on row 24 in level 5. The arm can **never** place a segment on any of the three color-8 blocks to its right (reaching x≥35 would first require occupying (29,24)); sliding the whole arm up/down is also blocked at the segment (29,x). The actual solution first pushes a color-9 block on the left to x=35 on row 12, then slides the whole arm downward. Color 9 hits color 8 and pushes it into the next row; the arm itself never enters the obstacle's row.

**(Test-based correction) Obstacles are visible.** Earlier text said they were “painted exactly like the background, invisible onscreen, discoverable only by bumping into them.” The color claim was correct (the sprite is entirely color 5 = `BACKGROUND_COLOR`), but **activity box `jtteddgeyl` is solid color 4 at layer −1, while obstacles are at layer 0**. They are drawn over the box, leaving a clearly visible **6×6 color-5 hole** inside it. Level 5 (29,24) and level 6 (29,26) both work this way.

**(Test-based correction) An obstacle blocks only one cell; the test checks the single pixel at the moved sprite's upper-left corner.** `qzvlbxkjgk` uses `get_sprite_at(x, y, "mkgqjopcjn")`, where x,y are the sprite's upper-left coordinates after moving. Obstacles are also 6×6 and grid-aligned, so the effect is exactly “cannot occupy or push into that cell.” Neighboring cells above, below, left, and right remain unaffected (level 5 (29,18) and (29,30) are both occupiable).

`jtteddgeyl` bounds the entire activity area (`box.x .. box.x + pixels.shape[1]*6`, the pre-scaling cell count × 6); blocks cannot leave it. The base and innermost arm segment actually sit outside it. `bnrdrdiakd` makes exceptions for “segments already outside the box” and “segments retracting toward the direction they came from,” so that segment can move legally. Blocks have no such exception and can never retract into the base cell.

**Selection has two requirements: `sys_click` and the pair table; both are necessary.** In the current version only bases with identity colors 6/15 have `sys_click`; colors 10/11 do not. Bases without same-color partners are also absent from the pair table. Therefore:

- In level 3 only the horizontal board arm is controllable; the color-11 vertical rack cannot be selected. The old version had `sys_click` on it, but it was already unselectable because it lacked a pair, so actual behavior agrees.
- **In level 4 only the initially selected horizontal loading arm is controllable** (`ejlpqgojjt`, (5,42)). It has no pair, but can move with directional inputs because it starts selected. Both paired color-10/11 vertical arms and their HUD templates lack `sys_click`; neither board nor HUD clicks can switch to them. Official targeted tests at (25,2), (37,2), (13,58), (37,58) all left the selection unchanged.
- Level 4 remains solvable: **move only the horizontal loading arm, delivering four blocks beneath the two fixed vertical arms so both templates match**. The official clearing trace has 29 directional inputs and zero clicks. It does not “load blocks, then switch to a vertical arm.” The old version allowed switching to the vertical arms, after which the unpaired horizontal arm could not be reselected; that old solution does not apply to the current version.

**Solver limitations**: The planner still treats all paired arms as clickable. The tested level-3/4 routes never attempted those unavailable switches, so this does not affect 8/8. Separately, after 13 steps in level 4, a fresh solver finished in 16 steps with zero clicks; this does not establish recovery from arbitrary intermediate states. [render_checks.py](../../../runtime/pixel/probes/render_checks.py) can rerun the source-tag checks, clearing witness, and this cut point.

**A failed translation may leave dirty state that consumes the entire next action.** Although translation is all or nothing, `bnrdrdiakd` may add some blocks to `self.pzzwlsmdt` (the highlight list) midway through. When `hgivzuhjvj` returns early because another segment fails, **it does not clear that list**. On the next `step()`, `if self.ljprkjlji or self.pzzwlsmdt:` clears highlights, rechecks, and saves, then calls `complete_action()`. That submitted direction/click/Undo **is neither executed nor charged**. Random probes on the old reconstructed engine reproduced this twice in level 7; this frequency was not measured on the current official engine. Planners should treat the residual field as a state difference; an unmoved board does not establish that the transition has fully ended.

**Limits of a single frame**: Base `sys_click` tags are invisible. Identical arm/block positions may conceal different Undo stacks, residual highlights as above, or exact remaining steps. The bar maps 196 steps onto only 64 pixels; exact remaining budget requires action history. Source tag lists for the fixed levels can serve as rule references, but do not imply that any frame reveals selection permissions on its own.

## Recognizing objects onscreen (visible geometric cues)

| Object | Appearance | Notes |
|---|---|---|
| Base | 6×6, with an **isolated central 2×2 identity color** (6 / 15 / 10 / 11); outer border color 4 (unselected) or 0 (selected) | The identity-color outline is a ring; only its center is 2×2, so the “isolated 2×2” is unambiguous. The rest of color-10/11 bases is color 5, effectively invisible |
| Base orientation | Two transparent pixels on the right (or bottom) expose arm segment 0 | Gap at `(x+5, y+2..3)` = right-facing; at `(x+2..3, y+5)` = downward-facing |
| Selection | All arm segments change 2→1, 3→2 | Read segment 0 through the gap: right-facing `(2,3)`=unselected, `(1,2)`=selected; downward `(3,2)`/`(2,1)`. The template arm lights up with its partner |
| Arm segment | Horizontal segments draw only the middle two rows, `3,2,2,3,2,2` / `2,2,3,2,2,3`; vertical ones draw only the middle two columns | Blocks cover only the middle; the leftmost column (topmost row) always remains exposed, allowing segment counting |
| Colored block | Solid 4×4 color block inside 6×6 (8 / 9 / 12 / 14) | Check lights may cover the central 2×2; identify from the 12 outer pixels |
| Check light | Color-0 2×2 at the exact center of the template segment | Lit = this position matches |
| Activity box | Solid color-4 rectangle, 30×30 or 42×42 | layer −1 |
| Obstacle | 6×6 color-5 hole inside the box | layer 0, drawn over the box |
| Rail | Color-2/3 stripes (`2,2,3,3,3,3,2,2`, an 8-long pattern repeated every 6), within a two-pixel-wide band on the base's midline | The base covers its own 6 pixels, but both probe points are just outside it |
| Budget bar | Row 53; left color-2 length = `ceil(64 × remaining steps / 196)`, right color 3 | Row 54 onward is HUD background color 4 |
