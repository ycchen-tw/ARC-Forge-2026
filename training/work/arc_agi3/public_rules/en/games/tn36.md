**Core rules**: The right half of the screen contains a “machine,” with a **7×7 board** (4×4 px per cell, top-left `(33,4)`; level 1 instead has a 9×8 board at `(14,9)`), a **block** in color 11, a **U-shaped target frame** in color 11/15, and an **instruction tape** and **run button** underneath.

The tape is a row of upright “columns,” each representing one instruction. **Each cell is one bit, read from top to bottom, with the LSB at the top**: a 6-cell column represents 1/2/4/8/16/32, giving instruction values 0–63 (level 1 has only 2 cells per column, values 0–3). A lit cell (color 5) means bit=1; a dark cell (color 1) means bit=0. To help distinguish cells, their patterns alternate between horizontal and vertical bars (cells 0,2,4 horizontal; 1,3,5 vertical). Clicking a cell flips its bit. The instruction count always equals the number of columns; leave unused columns at 0 (no operation).

All cell coordinates below are **0-based (column, row)**, with the board's top-left at (0,0).

Pressing run **first resets the block to its starting state**, then executes **one instruction per frame**, from left to right through the whole tape (the active column has a color-9 glow behind it). At the end:

- **The block's x, y, scale, rotation, and color must all equal the target frame's requirements** → clear the level (`next_level`). The predicate `vklyonlcrw` compares only these five properties and **does not check whether the block is still alive**. Thus, in theory, a block destroyed by spikes could still clear if all five match (none of the seven target frames is on spikes, so this situation does not arise).
- Otherwise, the block **returns to its starting state**. The attempt is discarded; edit the tape and run again.

The target frame is a U-shaped bracket opening in one direction, with a 2 px nub at the inner bottom. The block is 4×4 with 2 px missing from the middle of its bottom edge. Their “joint” must align—hence **rotation must also match** (the opening and nub indicate the required angle). The frame's color is the required block color. In coordinates, the frame extends one ring beyond the required landing position: **required position = frame sprite top-left +scale; required side length = frame side length −2×scale** (a scale-2 frame is drawn as 12×12 and requires an 8×8 block inside it).

**Instruction table** (verified entry by entry from `okllwtboml`; unlisted values do nothing, for example 0, 4, 32)

| Value | Binary | Effect |
|---|---|---|
| 1 | `000001` | Move left 4 px (1 cell) |
| 2 | `000010` | Move right 4 px |
| 3 | `000011` | Move down 4 px |
| 33 | `100001` | Move up 4 px |
| 34 | `100010` | Move left 4 px (same as 1) |
| 10 / 11 | `001010`/`001011` | Move right 8 px (2 cells) |
| 12 / 13 | `001100`/`001101` | Move left 8 px |
| 5 | `000101` | rotation +90 |
| 6 | `000110` | rotation −90 |
| 7 | `000111` | rotation +180 |
| 16 | `010000` | rotation +270 |
| 8 | `001000` | scale +1 |
| 9 | `001001` | scale −1 (minimum 1) |
| 14 | `001110` | Change color to 9 |
| 15 | `001111` | Change color to 8 |
| 63 | `111111` | Change color to 15 |

The direction encoding is deliberately irregular (up is 33 rather than 4; left has both 1 and 34). **The demonstration machine on the left must be used to infer the mapping**; this is the game's main induction challenge.

Codes 10–16 are unused in the example solutions in the table above, but **measurements confirm they work and are often cheaper**:

- `16` (rotation +270, equivalent to −90) requires flipping **1 bit**, half the cost of equivalent `6`. Similarly,
  use `1` (1 bit) rather than `34` (2 bits) for left, and `10` (2 bits) rather than `11` for right by 2 cells.
- `10`/`12` jump 2 cells and **test collision only at the destination**—even a wall in the intermediate cell is skipped.
  Level 7's first segment uses `10` to jump directly from (3,6) to (5,6), crossing the wall at (4,6).

**Action mapping** (`ACTION6` only)
- Click **a cell on the player's tape** → flip its bit.
- Click the **run button** (the color-9 circle at bottom right, `(53,54)` 9×9; at `(32,51)` in level 1 and `(42,54)` in level 2) → run the entire tape.
- Click **one of the selection buttons at bottom left** (9×9, y=54; level 2 x=7,17; levels 3–7 x=1,11,21,31(,41)) → select demonstration program i and **immediately play it once on the left demonstration machine**. The selected button turns color 9; the others are color 2.
- Click anywhere else → no effect, but **still consumes one progress-bar unit**.

**Run and selection buttons have different shapes** (the only reliable distinction for pixel object detection): run button
`sucqgkbuojsa` is a 9×9 **filled rounded disc** (color 9, 69 filled px), whereas selection buttons
`tozzsfsedoig`/`tozzsf1` are 9×9 **hollow square frames** (only 32 px, selected color 9, unselected color
2). Position alone is insufficient: in level 5, the rightmost selection button at `(41,54)` is **inside** the player machine's bbox
`(31,2)+32×61`. (`ytkjoffamq.rawolunrbj` checks selection buttons before the machine, so
clicking there switches the demonstration program rather than interacting with the machine.)

The run animation costs no additional actions: after the run-button click, the engine keeps stepping until the program finishes before `complete_action`, so “one click = the whole program runs” (fps=3 makes the step animation easier for humans to see).

**Special mechanics**

- **Demonstration machine (left)**: A color-3 gray panel holds a color-4 block and a **read-only** tape (background color 2). It has no target frame or run button; only selection buttons trigger it. Level-data `Programs / Positions / Rotations / scvkkws / Reset` are fed exclusively to this machine:
  - `Programs[i]` = instruction values of demonstration program i.
  - `Positions[i]` = starting cell, expressed as an **offset from the center cell of the 7×7 board** (for example, `[0,-2]` = 2 cells above center).
  - `Rotations[i] / scvkkws[i]` = initial angle and scale of the demonstration block.
  - `Reset[i]` = whether to return the demonstration block to its start after execution; all seven levels use `False`, so **the demonstration block remains at its endpoint**, showing its net displacement. Press the same selection button again to reset and replay it.
  - These demonstration data do not initialize the player's tape; levels 2–7 start at all 0, with level 1's `[3,0,3,0,0]` as the exception shown below.
- **Walls** (solid color-6 blocks): If movement or scaling causes overlap with a wall, that operation is **fully rolled back** (effectively a no-op). The block is neither pushed away nor killed.
- **Level 6 has one “fake wall”**: `wauzms-2` is drawn at `(37,0)` (cells (1,−1) and (1,0)).
  It looks identical to a real wall, but its sprite origin y=0 is **outside** the player-machine bbox (y≥2),
  so `nxexmixgsb(sprite.x, sprite.y)` in `hiwmavpjwg()` filters it out → **it is absent from the collision
  list, and the block can pass through**. This is the only such wall in all seven levels. A pixel-only solver cannot distinguish it,
  and conservatively treats it as a wall—the level-6 route does not use (1,0), so this has no effect.
- **The board has no boundary**: A program can move the block off the board or even off the panel; the code checks only walls and spikes.
- **Rotation and recoloring ignore whether the block is alive and perform no collision checks**: `cwtesiybfx`/`adjust_scale` both begin
  with `if not brvmvgfchj: return` (dead blocks do not move), whereas `rotate` and `knfgrcbayu`
  lack this gate. A spike-killed block therefore still rotates and changes color—this also explains how a “dead block could still clear.”
  For collision, the block has a square bbox of side 4·scale, unchanged by rotation, and all objects use
  `BlockingMode.BOUNDING_BOX`, so the entire collision system operates **cell against cell**, rather than pixel against pixel.
- **Checkpoint sockets** (color-11 dotted 4×4 frames): **At the instant execution ends**, if the block's bbox **overlaps** a socket and their scales match (this does not require equal x/y), that position becomes the block's new “start” for subsequent runs (the socket is hidden, appearing filled). This allows a route to span multiple runs; “displacements over 6 cells require a checkpoint” is false, since 10/12 each move two cells.
  The saved state is **more than position**: `mnvoffrbex()` saves all **five** properties—x, y, rotation, scale, and color—and `olrpupaury()` restores all five together. Saving on a socket therefore makes the **entire current pose** the new start: if you rotated, enlarged, or recolored before stopping there, the next segment continues in that pose. Existing solutions for the seven levels never change those three properties before saving, so the distinction is invisible there, but a solver must handle all five.
- **Retractable spikes** (color-12/13 stripes, color-14 end): A fixed 4×4 base plus a 14 px retractable rod. **All spikes switch extension state after instruction 3** (`jmwdvdqntf`, condition `pc % 3 == 2` **and not the final instruction**, so a 6-instruction program switches only once), and switch back at the end of a failed run. The resulting rule is simple: **retracted during the first 3 instructions, extended during the last 3**. The switching instant also triggers a collision check. Contact with a spike (the whole rod when extended, the base when retracted) **immediately destroys** the block: color-12/13 wreckage flashes for one frame, then movement/scaling are disabled while rotation/recoloring still work; a failed run revives it at the start afterward.
  - **Touching the base is always fatal** (the retracted collision shape is the base), not only when extended.
  - **Read extension direction from the image**: One whole edge of the base is color 14, the end against the backplate; **the rod extends
    away from color 14**. This is the only clue—the images seen while solving always show retracted spikes (a failed
    run switches them back); only intermediate execution-animation frames show the extended rods.
- **Progress bar**: A color-9 bar slides left 1 px per click, exposing a color-3 bar behind it; reaching the end triggers `lose`. In levels 6–7 it slides 1 px every 2 clicks instead.

Notes:
- The “verified solutions” in the table are routes actually executed by the **pixel-only** solver `runtime/pixel/solvers/tn36.py`
  against unmodified official source (7/7 levels cleared, 91 total actions, all resume tests passed).
  They are not guaranteed shortest; clicks include bit flips and run presses, and are all well below the progress-bar limits. Levels 3, 6, 7
  are cheaper than routes from early static inspection because they use the lower-bit-count codes `10`/`12`/`16`.
- Pixel-only parsing anchors (measured to be reliable):
  - **The largest color-0 connected component is the player machine**—the left demonstration panel uses colors 3/2; only the player
    machine uses 0. (The selection-button icons also contain a few color-0 pixels, so use the largest component,
    not the bounding box of all color 0.)
  - Horizontal lines across the panel's **entire width in color 0**: the 1st is the panel top, the 2nd is the tape top,
    and the last line is the tape bottom. The board lies between the 1st and 2nd, inset 1 px on each side.
  - Tape: horizontal bars occupy `(column x+1 .. column x+3)`, vertical bars occupy `column x+2`; **both centers are
    `(column x+2, cell y+1)`**, so sample that point to read the bit (5=1, 1=0). Column pitch is 5 px, cell pitch
    3 px, and tape height = `3·B + 1`.
  - Detect walls by whether a cell **contains any** color 6: the target frame (layer 1) covers a corner of walls (layer 0),
    so requiring the whole cell to be 6 misses several cells in levels 6 and 7.
  - Block: square side 4·scale; the notch side gives its angle (bottom 0 / left 90 / top 180 / right 270).
    Target-frame sprite top-left = required position − scale; its opening gives the required angle.
- Rotation codes 5/6/7/16 only change the `rotation` value. Official 0.9.3 `Sprite.render()` calls `np.rot90` directly with `k=(-rotation % 360)/90`, so **+90 appears clockwise**; there is no need to infer it via cn04. Clearing still compares rotation values.
