**Core rules**: The player moves on a board with 4×4-pixel cells (effectively a 16×16 grid), moving every **box** into a **target zone**. This uses **grabbing**, unlike ordinary Sokoban: face a box and press `ACTION5` to **grab** it. Subsequent movement carries the box with the player (keeping its relative direction, allowing both pulling and pushing); press again to release. Victory requires **all boxes inside target zones, with none held by anyone**.

> **When success is checked** (confirmed by measurement): `step()` proceeds “player action → helper robots → troublemaker robots → recolor → check `ymzfopzgbq()`.” Thus, when a helper robot drags the **last** box into a target zone, **that tick does not clear the level**—it still holds the box. Clearing waits until it releases on the next tick, costing one whole additional action. A player delivery likewise needs `ACTION5` to release, and robots may still steal the box on that tick. Which is faster depends on routes and ownership; timing alone does not settle it.

**Action mapping**
- `ACTION1-4` (up/down/left/right respectively): Move one cell and turn **facing** to that direction. **When empty-handed, facing changes even if a wall blocks movement** (`pjedoipwee` sets rotation before attempting movement); **while holding a box, facing stays locked**, preserving relative direction.
- `ACTION5`: Acts only on **the cell directly ahead** (`vwiozbtqgi` computes it from rotation), not “any adjacent cell.”
  - Holding a box → release it.
  - Box ahead → grab it. **This steals even a box currently held by a robot (or someone else)** (`xpcvspllwr` first makes the previous holder release).
  - **Troublemaker robot** ahead → **remove it from play** (any box it holds drops in place).

**Two autonomous robot types** (each player action updates helpers first, then troublemakers; moving, grabbing, and releasing each use that robot's tick, but a grab can end updates for its type early; see point 6)

- **Helper robot** (`kdweefinfi`, solid **color-12** 4×4): A fully automatic helper. When empty-handed, BFS moves it toward the nearest reachable cell adjacent to a box that is “unheld and not yet in a target zone” (when already adjacent, it grabs in box-list order; selection is not by distance to box centers). On reaching the box it grabs it; while holding, BFS drags it into a **target zone**, then releases. It **does not** steal held boxes or touch boxes already in target zones.
  Like the player, it has a locked relative direction while holding, so **it can get itself stuck**: grabbing from the wrong side can make delivery permanently impossible in that orientation (BFS returns None), leaving it stationary. The player can face the box and press `ACTION5` to steal it back; other actors moving aside or troublemakers stealing it can also change the situation.
- **Troublemaker robot** (`ysysltqlke`, solid **color-15** 4×4; when targeted by the player, **only its border** turns **color 11**, while the central 2×2 remains color 15—`uxricavavq` changes only sprite rows/columns 0/3. Confirmed by measurement; detecting it by “the whole cell has one color” misses the targeted cell): Almost symmetric code to the helper, but its destination is a **decoy zone**, and **it steals**—from the player, helpers, and even boxes **already in target zones** (the only held boxes it avoids are another troublemaker's). Deal with it when you see it: **face it and press `ACTION5` to dismantle it directly**.

**Pitfalls and source details**

1. This document previously described the troublemaker as a “key item that disappears when you approach and press `ACTION5` to pick it up,” and omitted helpers entirely. Both are actually autonomous AI updated each action: `dhrikuybfo()` calls `ynmgxjqkgh()` (helpers) then `aoeyzovteg()` (troublemakers). `ACTION5` facing a troublemaker means “dismantle,” not “pick up”—the difference is that it has already been interfering before you dismantle it.
2. Target and decoy zones differ only by a color-9 border (`fsjjayjoeg` vs `zqxwgacnue`); both have color-2 fill. This visual trap contributes to the difficulty of Levels 6-9.
3. Forbidden tiles block walking actors, not dragged boxes—`fuykgiiwit` checks `qthdiggudy` for the player's destination, but only collision for the box's destination. Thus “walk around the side while the box floats across forbidden tiles” is legal.
4. Robot BFS is **shortsighted**: Its occupancy map is a static snapshot computed when BFS runs. It does not recompute for other actors' movement along the path; it takes only the first path step and starts again next round.
5. Collision map `pkbufziase` registers only a sprite's **top-left cell**. This works for 4×4 boxes/walls/actors, but Level 7's two 64×20 / 64×16 floor markings are also collidable, so each blocks just one cell, at (0,44) and (0,0)—a harmless small defect that does not affect solutions.
6. **A robot grabbing something interrupts the entire update loop for its type** (confirmed by measurement: 499 grabs, no counterexamples): After a successful grab, `ynmgxjqkgh()` and `aoeyzovteg()` use `return`, not `continue`. Thus, on the tick when robot *i* grabs a box, robots *i+1* onward of the same type **do not move at all**. Exact simulation of Levels 4/8/9 (multiple robots of a type) must reproduce this `return`.
7. **Robot target sets contain no hidden state** (despite appearances): Helpers' target set `lkvghqfwan` is recomputed only at “level entry / grab / release” (`vyltpasvhc`), while troublemakers' `uuorgjazmj` is also recomputed while dragging (`lgirylubbp`). `lkvghqfwan` appears capable of going stale, but boxes move only while held, and held boxes are already excluded from `lkvghqfwan`—so it always equals a fresh recomputation. A simulator therefore need not separately save these two recomputable target caches; ownership and obscured regions may still require history, as points 8 and 9 explain.
8. **When a box is robot-held and directly ahead of the player, its border is color 3, not color 5**. Color 3 can mean either an unheld box or a robot-held box; one image cannot distinguish them. Color 5 says only “held by some robot,” without identifying which—also ambiguous when a helper and troublemaker stand beside it simultaneously. A robot's sprite.rotation is not its holding direction either: movement does not update rotation, so ownership must be inferred from actual relative positions. Both gaps require checking whether the previous tick's prediction matches.
9. **Do not guess target/decoy zones hidden under boxes**. This is the pixel-only solver's biggest trap: invent one target cell, and delivery there does not count, so the level exhausts its budget while “believed solved”; miss one cell, and the solver loops. Use **sound inference**: enumerate all rectangles consistent with visible pixels, and trust only cells that **every candidate agrees on** (target zones have color-9 borders, so one visible cell often uniquely determines the entire rectangle). Accumulate the rest using the fact that terrain never changes within a level. Level 6's (14,7) and several upper-left decoy cells in Level 8 are box-covered from the start and truly cannot be inferred—fortunately decoy zones affect only troublemaker prediction, not success.

### Sources and checks

Current `wa30-ee6fef47/wa30.py`: `on_set_level:899` (collision, targets, decoys, empty ownership map), `fuykgiiwit:996` (dragging/forbidden tiles), four BFS functions `1009–1102` (neighbor tie order left/right/up/down), `ynmgxjqkgh:1142`/`aoeyzovteg:1171` (sprite-list order; same-type update returns on grab), `yygfcvqoyx:1203`/`step:1248` (per-tick order, win before loss). Box/target/decoy/robot/wall/forbidden-tile inventories and sizes were checked for all 9 levels.

Each ACTION1–5 costs 1 budget unit; **wall hits and ACTION5 with nothing to grab also advance both robot types**. Even when action N exhausts the budget, the complete AI turn runs before checking success; it loses only if unfinished. The bottom bar's color 7 is the remaining fraction, color 4 the consumed portion. It overlays frame row 63, hiding the last pixel row of objects at the bottom edge; walls still block their original cells, so requiring all 16 pixels of those 4×4 wall cells to be color 5 misses them. Each level rebuilds the counter, ownership map, and target sets; no undo. Observations of fixed terrain can accumulate, but a single image still leaves ownership and obscured regions ambiguous; recomputable target sets do not imply that one image contains complete state. Official 0.9.3 probes for last-action win-before-loss (injected completed box positions, not a solving route) and budget exhaustion are in [review_e.py](../../probes/review_e.py).
