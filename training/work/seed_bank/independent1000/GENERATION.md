Generated by OpenAI dot + Astra Ultra. This document is compiled from the deliverer's method description
(GENERATION.pdf, 2026-10-05, 9 pages); the original ZIP and task files stay frozen.
Root's independent re-verification results are in a separate research note.

| Item | Count |
|---|---|
| Task packages | 1,000, `ind_0001`–`ind_1000`, only the current version kept per task ID |
| Stored examples | 8,813 pairs (train 5,740, test 3,073) |

## 1. Parents: pinned source, PASS tasks only

Source pinned at arc-forge `55a85ef8`; only tasks whose `seed.json` has `verification.status` PASS are picked:
training 984/1,000, evaluation 118/120, 1,102 usable in total (18 FAIL tasks excluded).

- Each task has at least two distinct parents, **at least one from evaluation**. Distribution: two parents 926, three 70, four 3, five 1.
- Parents are recorded in `seed.json`'s `provenance.parents`, some packages in the structured `provenance.nl_sources`;
  contents include task_id, split, pinned commit or URL, source-file SHA256, the mechanism actually borrowed, and for some an official pair replay.
- What is synthesized are **interdependent mechanisms**: the parents' mechanisms must jointly determine the same answer (e.g. hole count sets the object order, then colour and height propagate along that order).
  Mere recolouring, repositioning, or saving extra samples does not count as a new mechanism. Explicitly specified new interactions are allowed; provenance records only the borrowed causal mechanisms,
  and later-added graph algorithms, optimization, or physics rules are not credited to the original tasks.
- **Data contamination**: all 118 eligible evaluation tasks were used as design material (eval cited 1,467 times, training 612).
  After training or tuning on this batch, these eval tasks can no longer serve as an untouched held-out evaluation.

## 2. Generation pipeline: the model writes programs, the programs produce grids

Five Astra Ultra author roles design task by task, plus an independent quality-check role. The model writes rules, programs, and tests;
Python/NumPy does the sampling and pixel computation; grids are not drawn cell by cell by hand.

1. **Define the task first**: `seed.json` states the valid input domain, objects and control signals, order of operations, output size, and expected invariants.
2. **Solver**: `transform.py` computes the answer from input pixels only.
3. **Generator**: `generate_input.py` exposes `generate_input(rng, size_hint=None)` and `check_input(grid)`;
   internally there is usually a `generate_case` / `generate_pair` returning input, expected output, and latent scene data (names vary by task).
4. **Latent answer and pixel solving are computed separately**: the generator first draws objects, topology, counts, or control sequences, constructs the answer directly from the latent data,
   then draws the input; transform re-recognizes and computes from pixels, and the two are compared cell by cell. Using only the transform output as the answer would prove nothing beyond self-replay consistency.
   But some generators import parsing helpers from `transform.py`, so this is not full isolation; truly independent pixel reference solvers exist only for the 34 shipped tasks.
5. **Pick demonstrations that rule out simplified solutions**: authors implement easily mistaken alternative rules (sort by colour code, look only at the bounding box, ignore one parent mechanism, update only once, etc.)
   and pick train/test from the candidate pool on which they fail, adding paired counterfactuals, boundary conditions, and output colour coverage.
   This is not a uniqueness proof against unknown rules; train/test is the in-task demonstration split, not a training dataset split.

`seed.json` describes the rule and sources; the rng seed reproduces the sampling, and each author's seed set differs (see the per-task verification files);
the full-batch generation-contract check uses `202610401` throughout. Replay needs only Python + NumPy, no model or API.

## 3. Two examples

**`ind_0001` hole order determines attribute propagation**. Parents `evaluation/89565ca0` (count and order of 4-connected enclosed regions) and
`training/2601afb7` (reverse cyclic propagation of colour and height). Hole counts establish a cyclic order; each output column takes the previous object's colour
and the next object's hole count as height. `generate_case` draws 3–5 distinct hole counts and colours and builds the input from rectangles with inner walls;
the expected answer takes the latent values, transform recounts the enclosed regions. 4 train, 3 test; seeds 11, 29, 71, 103, 50 times each;
also tests wrong solutions such as colour permutation and colour-code order, position order, no swap, reversed swap. Classified `author_only`.

**`ind_0239` address relocation and shared objects**. Parents `evaluation/d35bdbdc` (colour-address references) and
`evaluation/3dc255db` (true pixel counting). From ordered root references, reachable objects are discovered first-in-first-out, contiguous space is allocated by true pixel count, and pointers are updated;
shared and cyclic objects are moved only once, and objects with the same content but different old addresses are allocated separately. Object sizes change later addresses and references determine discovery order,
so both mechanisms jointly determine the answer. The independent check enumerates discovery order by short paths and allocation addresses by prefix sums, reviewing 12 stored answers + 200 new cases,
classified `bounded_exact`.

## 4. Fixes and replacements

When a problem is found, add examples that rule out the wrong solution, or replace the whole task with a new mechanism. The task ID may be reused, but files and evidence must be re-matched to the version,
and the old task's pass records do not carry over; in the end only the current version is kept.

| Task ID | Early version (reason retired) | Current version | Review |
|---|---|---|---|
| `ind_0239` | area sort + filled/hollow split into two columns (too close to the old four-engine object family) | reachable-object relocation, shared-object dedup, address rewriting | limited independent review in this release |
| `ind_0627` | centroid addressing / polyline machine (mainly only swapped the sort encoding) | five-station multigraph, four joint probabilities of two query edges under a global spanning tree; answer computed by weighted Laplacian cofactors, the 10 train / 7 test re-verified by a linear system and transfer-current determinants | `author_only` |
| `ind_0861` | woven walls / distance-cycle colouring (too close to the wall-field family) | signed sparse reconstruction: three signed coefficients minimizing weighted squared error + L1; for the 15 train / 12 test, subgradients confirm each has a unique global minimum | `author_only` |

The targeted evidence for 0627 and 0861 only covers stored answers and named wrong solutions; `adds_full_review_status=false` in `RESOLVED_REVIEW_NOTES.json`.
Review counts follow `REVIEW_STATUS.json`.

## 5. Verification levels

| Level | Content and scope |
|---|---|
| Author side | 1,000 `validation.json` / `verification.json`, 200 each: latent-answer comparison, replay, format, wrong-solution counterexamples |
| Full-batch stored-answer replay | 8,813 pairs: valid input/output, `check_input`, same answer for array and list input, input not mutated, no duplicate stored inputs within a task |
| Full-batch generation contract | 5 per task, 5,000 total: same RNG replays, valid domain, output format, determinism, input not mutated; **no independent expected answer** |
| Limited independent review | 102 tasks whose whole file set matches the SHA256 at review time (34 newly done pixel reviews + 68 earlier reviews still matching the version); `ind_0486`'s `parent_scope.py` changed, listed as `bounded_earlier` |
| Rerunnable independent suite | 34 tasks (part of the 102 above): 316 stored answers + 200 new cases per task; versions locked |

The author field additionally has 882 PASS and 118 `VALIDATED_PENDING_NOVELTY_REVIEW` (the latter also had 200 author checks).
These are author-level labels, not release blockers, and cannot be used to claim the whole batch passed novelty review.
At release there were no known unresolved version blockers; `OPEN_REVIEW_NOTES.json` still lists batch-wide independent semantic review and blind difficulty testing as not done,
and `ind_0125` keeps the scope limit "the shared-movement support has no necessary counterexample yet".

## 6. Mechanical dedup

- **Stored grids**: this batch's 1,000, the 1,120 sources, the old 108 tasks, the old four-engine 1,000 tasks, 20,305 pairs in total;
  applying D4 rotation/reflection and one-to-one colour renaming to input and output together, there are no pair collisions, task collisions, or isomorphic train/test inputs.
  Cropping, scaling, different encodings, or general semantic equivalence are not covered.
- **Program structure**: the 1,000 transforms each of this batch and the old four-engine set (plus two batches of generators and the 291 / 290 obtainable source programs)
  compared as ASTs after normalization and constant abstraction; no clone groups. Of the 1,120 source tasks, 829 have no comparable program;
  the old 108 tasks are compared by grids only. The AST comparison follows only functions reachable within the same file and does not resolve dynamic loading.

No flag only means these checks caught no duplicates; it does not prove semantic distinctness. There are currently **no human or LLM blind-solve rates,
solve times, or stratified difficulty**, so equivalence in difficulty to ARC-AGI-2 cannot be claimed; some tasks add graph, numeric, or optimization concepts,
and being able to run the program does not mean a solver can infer a unique rule from a few demonstrations. To use them as a benchmark, first freeze the task pool and scoring protocol,
then run blind solving, remove source overlap, and split grouped by mechanism.

## 7. Usage and rerun

This directory is the unpacked root minus two kinds of large files: the 116 `author_cases.json` (431 MB) and the offline `index.html` (21 MB),
which are stored together with the two original ZIPs in `$ARC_RUNS/seed_bank/20261005-independent1000/` (`full-extras/` keeps the original directory structure).

```bash
cd work/seed_bank/independent1000
../../../.venv/bin/python validate_examples.py --jobs 16                 # 8,813 stored answers
../../../.venv/bin/python validate_examples.py --jobs 16 --generated 5   # plus 5,000 generation-contract checks
../../../.venv/bin/python validate_examples.py --ids ind_0001 ind_0239 --generated 1 --output /tmp/replay.json
uv venv /tmp/ic-venv -p 3.12 && uv pip install -p /tmp/ic-venv/bin/python numpy==2.3.5 scipy==1.17.0
/tmp/ic-venv/bin/python independent_checks/run.py --jobs 2 --output /tmp/ic-results   # 34 tasks; do not add -O
```

The shared `.venv` has no SciPy, so the independent checks use a separate venv; point `--output` outside the repo so results do not land in the task-pool directory.
On 2026-10-06 root reran `ind_0239` this way: PASS (12 stored answers + 200 new cases).

Tested environment: Python 3.12.14, NumPy 2.3.5. The independent suite checks the SHA256 of tasks and check programs before running,
and refuses on missing files, added files, or version mismatch; results are written to `independent_check_results/run-*/`.

Generate new inputs inside a single task directory, in a separate Python process, to avoid same-named modules of different tasks contaminating each other:

```python
import numpy as np
from generate_input import generate_input, check_input
from transform import transform
x = generate_input(np.random.default_rng(20261005)); assert check_input(x); y = transform(x)
```

Some per-task `verify.py` / `make_task.py` rewrite `task.json` or the verification files; copy to a working copy before rebuilding the author pipeline.
The 116 tasks that reference `author_cases.json` must first be copied back from `full-extras/packages/<id>/`.
